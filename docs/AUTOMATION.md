## ١. سكربتات Git التلقائية

Git يقدر يشغّل سكربتًا **من نفسه** عند لحظات معيّنة. المصطلح الإنجليزي لها **git hooks**.
عندك ثلاثة، كلها في مجلد `.githooks/`:

| السكربت | متى يشتغل | وش يسوي |
|---|---|---|
| `pre-commit` | **قبل** تسجيل الـcommit | يرفض الـcommit لو عدّلت كودًا يُنشر بدون ما ترفع رقم النسخة، ثم يفحص **العقود** بين الملفات (القسم التالي) |
| `post-commit` | **بعد** كل commit | يعيد بناء خريطة المعرفة (القراف) في الخلفية |
| `post-checkout` | عند `git checkout` | يزامن القراف مع الفرع الجديد |

مربوطة عبر الإعداد:
```bash
git config core.hooksPath .githooks
```

### حارس النشر (`pre-commit`) — الأهم

**المشكلة اللي يحلّها**: النسخة مكتوبة في **كل المواضع** عبر ٨ ملفات (`index.html` عدّة مرّات، و`js/app.js`، و`version.json`، و`manifest.json`، و`admin.html`، و`privacy.html`، و`get/index.html`، و`CLAUDE.md`) — العدد الدقيق لكل ملف يطبعه `npm run release:check`، ولا يُكتب هنا لأنه يتغيّر. لو عدّلت كودًا ونسيت ترفعها، الأجهزة تظل على النسخة القديمة من الكاش — **الإصلاح ما يوصل ولا جهاز**، وما فيه أي رسالة خطأ تخبرك.

صار عندك فعلًا في الـcommit رقم `ea6c74e`.

فالحارس يوقفك:
```
✖ check-release: this commit ships code but does NOT bump the version.
    Fix:  npm run release  &&  git add -u
```

**لتجاوزه** (لو التعديل توثيق فقط ومو كودًا يُنشر):
```bash
SKIP_RELEASE_CHECK=1 git commit -m "..."
```

### فاحص العقود (`check-contracts`) — يشتغل في نفس الـpre-commit

```bash
npm run check            # يفحص كلّ العقود بين الملفات، بدون تعديل
```

**المشكلة اللي يحلّها**: التطبيق ثلاثة عشر ملف JS (العقد ١ يطبع قائمتها بترتيبها) تشترك في نطاق واحد، وقاعدة بيانات، وعامل Cloudflare، ولوحة تحكّم — وكثير من الأشياء فيه «لازم تطابق» شيئًا في ملف آخر، وما كان يحرسها إلا تعليق. الفاحص يقرأ الملفات ويقارن الطرفين ويطبع بالضبط وش اللي اختلف. أمثلة على ما يفحصه:

- ترتيب تحميل السكربتات = ترتيب الاعتماد بينها.
- كل مفتاح ترجمة موجود بالعربي **و**بالإنجليزي.
- كل جدول أو دالة أو حاوية يناديها التطبيق موجودة فعلًا بعد تشغيل ملفات `backend/migrations` بالترتيب، وأسماء وسائط كل `rpc()` تطابق تعريفها في SQL.
- مفاتيح `localStorage` كلها من السجل الواحد في `js/cloud.js`، ما فيه نسخة مكتوبة بالحرف في مكان ثاني.
- كل رسالة خطأ يرجّعها العامل لها ترجمة في التطبيق.
- أرقام الـAPK في `version.json` = أرقام `build.gradle`، و`js/health.js` ما ينادي إلا دوال معلنة في الإضافة الأصلية (Kotlin).
- **لوحة التحكّم تحسب نفس أسبوع التطبيق** (يبدأ الأحد): دالة `admin_user_stats()` في SQL، وحسابا الأسبوع في `admin.html`، وكل عبارة «الأسبوع من …» — كانت اللوحة تحسب من السبت والتطبيق من الأحد، فيطلع للمستخدم نفسه رقمان للالتزام في نفس الصباح.
- العناصر الثابتة في `index.html` اللي يبحث عنها الكود بالاسم (شريط التنقل، جذر النوافذ، التوست…) موجودة فعلًا — تغيير اسم واحد منها كان يبيّض الشاشة كلها.
- جدول الأخطاء `client_errors` يقبل كل نوع خطأ يرسله التطبيق — نوعان كانا يُرفضان بصمت، فسجلّ الأخطاء في اللوحة ما كان يستقبلهما.
- الأيقونات: كل اسم أيقونة في الكود موجود في مجموعة `ICONS` (الاسم الغلط يرسم فراغًا بلا خطأ)، والنسخ السبع المكرّرة خارجها مطابقة للأصل.
- العامل (Worker): أطول تعليمات يرسلها التطبيق (الصورة، الصوت، دفعة الوصفة) تدخل ضمن حدوده، وقائمة الأصول المسموحة تشمل كل منفذ يشتغل عليه خادم التطوير.
- أي دالة في قاعدة البيانات سُحبت صلاحية تنفيذها من الزوّار تبقى مسحوبة: حذف الدالة وإعادة إنشائها يعيد الصلاحية تلقائيًا (صار فعلًا في الترحيل ١٩، وأصلحه ٢٣).

**ما فيه تجاوز له.** لو كسر عقدًا، أصلح الطرف الغلط — ولو المراجعة لقت تعليق «لازم يطابق» جديد، أضف عقدًا في `scripts/check-contracts.js` بدل ما تصلح الحالة بيدك.

## ٢. الفحص على GitHub (CI) — الحزام مع الحمّالة

الـ`pre-commit` فوق حمّالة ممتازة، لكنها **محلّية**: تشتغل على جهازك أنت فقط، وبعد
أن تُفعّلها بـ`npm run hooks`، ويمكن تخطّيها بـ`--no-verify`. وGitHub Pages ينشر
الفرع **مباشرة** بلا بناء وبلا بوّابة — فأيّ شيء يفلت من الخطّاف يصير حيًّا عند كلّ
مستخدم في أوّل فتحة للتطبيق.

`.github/workflows/ci.yml` يشتغل على **كلّ push وكلّ pull request** ويفحص أربعة أشياء:

| الخطوة | ماذا تفحص |
|---|---|
| `npm run check` | كلّ العقود (٦٧ عقدًا في v401، والأمر نفسه يطبع العدد) — ترتيب السكربتات، علامات النسخة، الترجمة، اتّفاقات الواجهة مع الباك إند، بصمات المكتبتين، أسماء القمّة المكرّرة، رموز CSS غير المعرَّفة، وقاعدة كغ↔رطل الواحدة، ومفتاح سياق واحد لكل مفهوم، ولا دالّة ميتة في ملفات العرض، ولا تعليق CSS يفتح تعليقًا داخله، ورابط الـAPK على مضيف يفتحه التطبيق، وترتيب السكربتات المكتوب في الوثائق = الحقيقي |
| `node scripts/lint.js --strict` | الفاحص (ESLint) بخمس قواعد من علل المشروع نفسها — معالجٌ عارٍ يستقبل الحدث مكان وسيطه (v348)، يومٌ تقويميّ من `toISOString()`، `new Date('نصّ')`، `localStorage` في كود العرض، `.view.active` داخل رسم (v324) — مع `no-undef` الذي يمسك اسمًا مُخطَّأ قبل أن يصل هاتفًا |
| `node scripts/test-all.js --strict` | كلّ مجموعات الاختبار (أربع عشرة في v401) — ومنها `test-fingerprint.js`: يرسم العشرين شاشة في اللغتين والوضعين وعرضين (١٦٠ خلية) ويرفض أيّ خطأ صفحة أو شاشةٍ فارغة أو مفتاح ترجمةٍ خام أو أيقونةٍ فارغة أو رسمٍ يعلّق؛ و`test-i18n.js` (v399): يرفض العامّية في كلّ نصّ عربي وفي الكتالوج، ويثبّت مصطلحًا واحدًا لكلّ مفهوم، ويفحص صيغ العدد (واحد، اثنان، ٣–١٠، ١١+) |
| `npm run release:check` | تطابق علامات النسخة بعضها ببعض |

**وهو يُنزّل متصفّحًا، وهذا بيت القصيد.** المجموعات التي تفتح متصفّحًا
(`test-startup.js` و`test-sync-status-ui.js` و`test-fingerprint.js`) تحتاج Playwright،
وتقود Google Chrome المثبَّت على الجهاز. على جهازك إن لم يُنزَّل، ترمي خطأ
يسهل قراءته كضجيج — و**ثلاثة أعطال حقيقية اختبأت خلف ذلك الصمت**: v316 وv322
وإعادة بناء قائمة المشتريات في v329، وهذا الأخير لم يُكتشف إلّا حين شُغّلت المجموعة
لأوّل مرّة فعلًا. في CI تعمل دائمًا، و`--strict` يجعل التخطّي **فشلًا**، فلا يمكن
لتلك الثغرة أن تُفتح ثانية.

> Playwright وESLint يُنزَّلان بـ`--no-save`: لا يدخلان `package.json` ولا يُشحنان أبدًا. قاعدة
> «لا تبعيّات جديدة» تخصّ الحزمة التي يُنزّلها المستخدم، ولا شيء هنا يصلها.
>
> ⚠️ **في أمرٍ واحد، لا أمرين.** التثبيت بـ`--no-save` يشذّب كلّ حزمةٍ ليست في الملفّ —
> فأمرٌ ثانٍ لـESLint حذف Playwright بصمت، وقرأت المجموعتان كأنّ المتصفّح ناقص. وESLint
> مثبَّتٌ على النسخة ٩ لأنّ العاشرة أسقطت `globals` فانهار الإعداد على تبعيّةٍ لم يُعلنها أحد.

### أوامر جاهزة عندك

```bash
npm run check        # العقود كلّها
npm run lint         # الفاحص (يُعلن التخطّي بصوتٍ عالٍ إن لم يكن مثبَّتًا)
npm run lint:strict  # الفاحص الغائب = فشل — وهذا ما يشغّله CI
npm test             # كلّ المجموعات (التخطّي مسموح ومُعلَن)
npm run test:strict  # التخطّي = فشل — وهذا ما يشغّله CI
npm run verify       # العقود + الفاحص + المجموعات معًا

# شبكة البصمات — لإثبات أنّ خطوة إعادة هيكلةٍ لم تغيّر شيئًا (أداةٌ محلّية، ليست مجموعة اختبار):
node scripts/fingerprint-net.js matrix --tag before   # ٨ سياقات × ٢٠ شاشة، ~٥٠ ثانية
# …الخطوة…
node scripts/fingerprint-net.js matrix --tag after
node scripts/fingerprint-net.js diff before after     # صفر فروق، أو كلّ فرقٍ مسمًّى بشاشته
node scripts/fingerprint-net.js modals --tag before   # الأوراق والحوارات كلّها فوق بياناتٍ مزروعة، ~١٫٥ دقيقة
node scripts/fingerprint-net.js modals --tag after && node scripts/fingerprint-net.js diff before after
# (لكلّ ممرّ ملفّه: .fpnet/<tag>.views.json و<tag>.sheets.json، و diff يقارن الاثنين)

# قياس التصميم ومسارات النقر (أدوات محلّية، ليست مجموعات اختبار):
node scripts/ux-audit.js --tag pass1                  # ٢٠ شاشة ببيانات: مساحات النقر، التباين، ما يُقصّ، الطيّة
node scripts/ux-audit.js --text-lg --tag big && node scripts/ux-audit.js --compare pass1 big   # «خطّ أكبر»: أيّ صندوق يُقصّ
node scripts/ux-flows.js                              # عدد النقرات من الرئيسية لأربع كتابات يومية، مُثبَتة من قاعدة البيانات
```

**القاعدة:** لا يُوثق بفحصٍ جديد إلا بعد أن يُرى وهو **يفشل** على العيب الذي كُتب له
(يُزرع العيب، ثم يُعاد الملف كما كان بايتًا ببايت). وإعادة الهيكلة بلا تغيير سلوك تُثبت
بشبكة البصمات (صفر فروق) وبالمجموعات.

**لتشغيل الفاحص والمجموعتين اللتين تحتاجان متصفّحًا على جهازك — أمرٌ واحد:**
```bash
npm i --no-save playwright eslint@9 globals && npx playwright install chromium
```

## ٣. أمر الإصدار

```bash
npm run verify           # البوّابة: العقود + الفاحص + المجموعات — أولًا
npm run release          # يرفع النسخة في كل المواضع ويعيد قراءتها — ولا يشغّل أيّ اختبار
npm run release:check    # يفحص العلامات فقط، بدون تعديل
```

> ⚠️ **`npm run release` لا يشغّل اختبارًا.** كان هذا السطر يقول «ثم يتحقق منها» والمقصود
> العلامات فقط، فخرجت v383 وv384 وv385 على هذه القراءة. البوّابة هي `npm run verify`.

بعده: `git add` للملفات بأسمائها (أو `git add -u`) ثم commit ثم push. GitHub Pages ينشر خلال دقيقة تقريبًا.

> ⚠️ **`git add -u` لا `git add -A`.** الأولى تُدرِج المعدَّل من الملفّات المتتبَّعة
> فقط ولا تستطيع أن تلتقط ملفًّا غير متتبَّع؛ والثانية تكنس كلّ شيء في الشجرة —
> ومنها ملفّاتك الخاصّة في `docs/` — إلى مستودعٍ **عامّ**، بلا رجعة.

**لا ترفع الأرقام يدويًا.** السكربت يعيد قراءة الملفات من القرص بعد الكتابة ويفشل لو اختلف موضع واحد.

### التراجع عن إصدار سيئ
كل الأجهزة تحمّل نفس الرابط الحيّ، فالإصدار السيئ يوصل الجميع دفعة واحدة.

```bash
git revert <رقم-الcommit-السيئ>
npm run release          # للأمام دائمًا
git add -u && git commit && git push   # -u لا -A: لا تكنس ملفًّا غير متتبَّع
```

⚠️ **لا ترجع بالرقم للخلف.** المحدِّث يقارن الأرقام، والأجهزة **لا تنزل** لنسخة أقدم — بتعلق على السيئة.

## ٤. خريطة المعرفة (القراف)

تتحدث تلقائيًا بعد كل commit. مخرجاتها في `graphify-out/`:

| الملف | وش هو |
|---|---|
| `graph.html` | القراف التفاعلي — **افتحه بالمتصفح** |
| `graph.svg` | صورة للّصق في README |
| `GRAPH_REPORT.md` | تقرير مكتوب |
| `wiki/` | مقال لكل مجتمع |

**تكلفة التحديث التلقائي: صفر** — الكود يُقرأ ببنية الشجرة (AST) بلا ذكاء اصطناعي.

- `.graphifyignore` يستبعد المكتبات الخارجية والصور، عشان القراف يوصف **مشروعك** لا مكتبات غيرك.
- `scripts/graph-crossfile.js` يضيف الروابط بين الملفات، لأن التطبيق **ما فيه أي `import`** — الملفات تتواصل عبر متغيّرات عامة (`window.DB`)، وقارئ الشجرة لا يراها.
- تعديل **الوثائق** يحتاج تمريرة يدوية (تحتاج ذكاءً اصطناعيًا) — التلقائي يغطي الكود فقط.

## ٥. أشياء **لا** تتحدث تلقائيًا

| الشيء | متى يلزم | كيف |
|---|---|---|
| **قاعدة البيانات** | عند تعديل أي `backend/*.sql` | تشغيل يدوي: لصق في محرر Supabase، أو عبر أداة Supabase MCP إن كانت متاحة في الجلسة. وفي الحالتين يُسجَّل المسار والتاريخ في جدول `backend/README.md` |
| **عامل Cloudflare** | عند تعديل `backend/worker/gemini-worker.js` | `cd backend/worker && npx wrangler deploy` — لم يعد يحتاج لصقاً في اللوحة منذ v306. المفتاح السرّي `GEMINI_KEY` محفوظ على العامل نفسه ويبقى بعد كل نشر. |
| **إعدادات الحسابات** | مرة واحدة، بيدك | في لوحة Supabase ← Authentication: أقل طول لكلمة السر ٨، وحماية الكلمات المسرّبة، وقرار التسجيل المفتوح (إمّا إغلاقه والدعوة يدوياً، أو تأكيد البريد مع كابتشا). لا يمكن ضبط أي منها من الكود. |
| **المعلَّق حاليًا (v401)** | بيدك، مرّة واحدة | `backend/pending/30_ai-budget-and-caps-v26.sql` لم يُطبَّق (ميزانية الذكاء اليومية تفشل مفتوحة حتى يُطبَّق — `backend/README.md` §2)؛ والعامل يحمل تعديلات v391 وv397 ووضع الوصفة (v399) ولم يُنشر بعد: `cd backend/worker && npx wrangler login && npx wrangler deploy` ثم فحوص الهاتف في `docs/RELEASE-NOTES.md` ← v400 |
| **APK جديد** | **فقط** عند تعديل أصلي (إذن، إضافة Capacitor، كود جافا/كوتلن) | راجع `docs/ANDROID.md` و«APK signing» في `CLAUDE.md` ← Deploy: ملف `~/.android/debug.keystore` على جهازك هو هويّة التطبيق — خذ منه نسخة مشفّرة خارج الجهاز (لا في git)، وأيّ جهاز جديد يجب أن ينسخه إلى `~/.android/` قبل أوّل بناء، وإلا فالـAPK التالي لا يُثبَّت فوق الحالي |
| **فحص الحسابات الحيّ** | عند الحاجة فقط، بقرارك | `node scripts/verify-convenience-live.js --live` ينشئ حسابين مؤقّتين على الموقع الحيّ ويختبر عزلهما ثم يحذفهما — لا يعمل بلا `--live`، وليس جزءًا من أيّ بوّابة |
| **مراجعة المكتبتين المُضمَّنتين** | عند كل بناء APK، وكلما استُبدل أحد الملفّين | `js/vendor/SOURCES.md` يحمل الحزمة والنسخة بالضبط ورابط المصدر وبصمة SHA-256 لكلٍّ منهما، وفيه الأمران اللذان يُعيدان التحقّق. العقد ٣٣ يرفض أيّ التزام تغيّرت فيه بايتة من الملفّين دون تحديث الكتلة نفسها — لكنّه **لا يعرف** إن ظهرت ثغرةٌ جديدة في النسخة المثبَّتة، وهذا ما تفعله هذه المراجعة. |

### مهم عن الـAPK
التطبيق **قشرة تحمّل الرابط الحيّ**. يعني تعديلات الويب (JS/CSS/HTML) **توصل للمستخدمين تلقائيًا** عند فتح التطبيق، **بدون إعادة تثبيت**.

فلا تبني APK جديدًا لتعديل ويب — ما راح يغيّر شيئًا للمستخدم، وبيطلب منه إعادة تثبيت بلا فائدة.
